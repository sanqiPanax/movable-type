# Movable Type · 项目需求文档（v0.1 草案）

> 状态：**idea 阶段**，本文档只定义"要做什么、为什么"，不含实现
> 建立：2026-09-21
> 命名：`movable-type`（GitHub 同名仓库实测 0 个）
> 一句话：**把任意信息源渲染成一份"会动的旧报纸"的引擎**

---

## 0. 这个项目是什么

一份参考**旧报纸版式**的网页：有报头、分栏、板块、要闻区。**版面默认有一套初始排布，用户也可以按自己偏好重排。**

它和普通新闻阅读器的区别有两点，都很关键：

> **一、版面里的内容是活的。** 图片会动，翻页时文字会散开再重组。
>
> **二、版面是"被编辑过的"，不是信息流。** 版面容量有限（一版大约容纳 8~15 条），而来源每天给几百条。**由 AI 当主编做取舍**——哪条上头版、哪条只配一个豆腐块、哪条干脆不上。取舍之后再排版。

反过来，它和市面上那些"哈利波特魔法报纸"玩具的区别也很清楚：

> **它是引擎，不是演示页。** 输入是任意信息源，输出是版面；聚合、编辑、渲染各司其职，每层都可替换。

**定位（已拍板）**：一个**信息聚合平台**——自己从多个来源收集信息，由 AI 主编在有限版面下做取舍与排布，最后交给确定性渲染引擎落成版面。三层分工见 §5。
**受众（已拍板）**：面向全球开发者，README 英文为主 + 中文版。

## 1. 为什么是这个方向（立项依据，均已实测）

### 1.1 查重结论：坑没被占，但隔壁很挤

对 GitHub 跑了 10 组关键词、去重后触及 **62 个仓库**：

| 赛道 | 现状 | 代表 |
|---|---|---|
| RSS → 报纸版式 | **已有人在认真做** | `j6k4m8/goosepaper` 342★（每日报纸投 reMarkable）、`thesephist/unim.press` 249★（Reddit→NYT 风）、`MatthK/Selfoss-Webfront` 132★、`harshit181/RSSPub` 131★ |
| 哈利波特"魔法报纸" | **全是玩具级，没有例外** | 全部 **0~1★**：ARKit demo、课程作业、个人 portfolio |
| **"会动的报纸 + 真实信息源"** | **空缺** | 最接近的 `kjames2001/daily-tech-prophet` 仅 1★，且只吃 Reddit |

**推论**：真正没人做的是"**让版面上的内容动起来**"这一层。我们的位置卡在这个缺口。

### 1.2 "图会动"的三条供给，成本从零到有

实测数据：

- 开源项目 README 自带 GIF/视频的 = **36%（5/14）**，有静态图的 = **71%（10/14）**
  → **大部分条目没有现成的动图可用**，必须自己造动。
- 新闻配图抓取覆盖率：修好懒加载后 **83%**（修之前 10%）
  → 图能拿到，但拿到的是**静止的图**。

所以动图供给分三档，按优先级：

| 档 | 手段 | 成本 | 状态 |
|---|---|---|---|
| **A** | 源本身就带动图（项目 README 的 demo.gif、视频站封面） | 0 | 现成，覆盖率 36% |
| **B** | 静态图 → Ken Burns 慢推拉 / 程序化动图（图表自绘） | 0 | 立刻可做，永不失败 |
| **C** | 静态图 → **真·图生视频** | 见下 | 本地可跑 |

### 1.3 关于"以后算力会变强"（用户判断，记录在案）

用户观点：*图生视频/文生视频会越来越强、越来越便宜，这个问题可以靠时间打磨过去；当前甚至可以先直接用视频或 GIF 代替。*

**这条判断在架构上意味着**：视频生成必须是一个**可插拔的 provider**，而不是核心逻辑。今天用占位视频/GIF，明天换成本地模型，后天换成云 API——**引擎本身不该为此改一行代码**。

### 1.4 C 档的现状：本地已具备，云端不具备（实测）

**云端不可用**（2026-09-21 实测）：

```
plan-v3-chat   HTTP 400  InvalidSubscription
               Your account (2123201202) does not have a valid AgentPlan subscription
v3-chat        HTTP 401  AuthenticationError
视频生成接口     HTTP 401  AuthenticationError
```

→ key 本身有效（能读到账号 ID），但**订阅已过期、按量付费通道未开通**。要走云视频需新开 key 或开通 Seedance 模型。

**本地已具备**——`F:\ComfyUI` 已装，且已有：

| 资产 | 大小 | 说明 |
|---|---|---|
| DynamiCrafter 1024 / 512 (fp16 pruned) | 2.93 GB ×2 | **图生视频**，专为"让静图动起来"设计 |
| LongCat Avatar 1.5（lora + vae） | 2.35 + 0.47 GB | 音频驱动数字人 |
| 插件 DynamiCrafterWrapper / LongCat_Avatar / VideoHelperSuite | — | 管线现成 |

显卡：**RTX 5070 Laptop / 8151 MiB**。DynamiCrafter（2.93GB）在 8GB 上**跑得动**，产出 ~2 秒 / 1024×576。

> **判断**：报纸栏里图片显示尺寸只有 ~600×330，"稍微有点不对"在这个尺寸下看不见。
> **所以"图会动"这根柱子立得住，且零边际成本、离线、不外传。** 代价是速度与 2023 年画质。

**尚未验证**：DynamiCrafter 的实际出片质量与耗时（**这是全项目唯一还靠猜的环节，应尽快跑一条样片**）。

## 2. 核心需求

### R1 · 版面（旧报纸版式）

- 报头：刊名、日期、期号、滚动快讯
- 分栏：多栏网格，栏间细线，双线分隔
- 板块：要闻 / 科技 / 产业 / 文化…（栏目可配置）
- 版面元素：主标题、副标题、署名行、正文、图窗、图注、引文块、栏目标签、页码/页码风格
- 视觉基调：**旧报纸**——纸纹、衬线字、首字下沉、墨色、有限的彩度

### R2 · 可重排（用户偏好）

- **默认初始排布**：开箱即用，不用配置
- **用户可重排**：调整栏目顺序/位置、各板块占比、选择哪些源进哪个板块
- 重排的产物应可**保存/导出/分享**（配置文件或 URL 参数）
- ⚠️ 需要定义"排布"的数据结构——这是 R3 的前提

### R3 · 版面模型（Paper Model）—— 本项目的真正内核

引擎项目的核心资产不是动效，而是**那份描述"一页报纸长什么样"的模型**。

必须定义：

- 板块（section）→ 版面（page）→ 区块（block）→ 文本/媒体 的层级
- 每个区块的**权重/优先级**（决定谁上头版、谁占多大）
- **图文绑定关系**（图必须跟着它自己的那条新闻走，不许错配）
- 面向排版的元信息：栏数、字号档位、是否首字下沉

> **v1 的交付物本质是「一个 schema + 一个渲染器」。** schema 定死了，适配器和主题才能长出来。

### R4 · 文字动效（分三种场合，已确认）

用户原话：*"在单张页面时，它保持不动，或者带有像魔法波浪一样的动态特效。翻到下一个版面时，它就像文字飞来飞去，重新组合成新的段落了一样。"*

| 场合 | 效果 | 优先级 |
|---|---|---|
| **阅读中** | 保持静止（默认）；可选"纸面波浪"轻微起伏 | v1 |
| **入场** | 墨迹擦入 + 头条打字机 | v1（已验证） |
| **翻页** | **一段文字散开 → 重组成另一段** | v1 招牌 / 技术待定 |

### R5 · 翻页变形（本项目最难、也最值钱的部分）

见 §4 专门章节。

### R6 · 图会动

- 按 §1.2 的 A/B/C 三档供给，通过 **motion provider** 插拔
- 必须有 **fail-safe**：任何 provider 失败/超时 → 自动退回 Ken Burns，**绝不允许版面出现空白或破洞**
- 生成必须**离线预生成 + 缓存**：视频生成要几分钟，**不能在打开页面时现算**

### R7 · 数据源适配

- v1：RSS / 通用 JSON / Markdown
- 必须是**薄适配层**：适配器只负责把外部数据翻译成 Paper Model，不含排版逻辑
- **必须内置示例数据**：别人 clone 下来要能一条命令看到效果，否则打开是空白页

### R8 · 导出（连接内容生产）

- 版面 → 静态图（PNG，做封面/配图）
- 版面 → 短视频（MP4，发公众号/头条/小黑盒）
- ⚠️ 这条是**防"看一次就腻"的重要手段**：让它除了好看还能干活

### R9 · 输出形态

- **纯静态 HTML**（单文件或静态站），可托管 GitHub Pages
- 零依赖为默认档；重动效（粒子级）作为**渐进增强**，不可用时自动降级

### R10 · 信息采集（聚合层）

- 从多个异构来源收集条目：RSS / API / 网页 / 已有聚合器输出
- 必须做：去重（跨源同一事件聚类）、时间归一化、来源分级
- ⚠️ 采集失败必须**退化为缓存**，不许让版面开天窗
- 参考实现：用户已有的本地信息台 `newsdesk`（20 源、462 条实测可用）

### R11 · AI 主编（编辑决策）—— 本项目核心创新

见 §5 专门章节。

### R12 · 图片处理

- **选哪张**：从条目候选图里挑，且图与稿**结构上绑定**（不许错配）
- **怎么裁**：源图宽高比各异，栏位比例固定 → 必须有焦点裁切，否则切掉主体或拉伸变形
- **动不动**：只有值得的图才花算力生成视频——**这本身就是一个编辑判断**

详见 §5.6。

## 3. 已定的技术约束（实测得出，不是猜的）

### C1 · 逐字定位性能不是问题

Range API 逐字测量实测：

| 指标 | 实测值 |
|---|---|
| 单字符定位 | 4.5 μs |
| 全页 2170 字定位总耗时 | **9.8 ms** |
| 137 字标题（多节点） | 0.2 ms |

→ **翻页变形的位置采集成本可忽略**，可以每次翻页实时测，不必预缓存。

### C2 · 动效会破坏文本节点结构 ⚠️

实测：标题在打字机动画中 `childNodes = 29`；动画结束后 `childNodes = 138`，而文字只有 **137 字**。

→ **"逐字打字机"和"段落级变形"是冲突的**：动效把文本切成了碎片节点。

**设计要求**：动效层与文本层必须解耦——
- 文本层：始终维护**干净、连续**的文本节点（供定位、选中、搜索）
- 动效层：只做视觉变换，**不改写 DOM 结构**；或动效结束后必须**还原**结构

### C3 · 动画中的元素位置读数不可靠 ⚠️

实测：给元素设置 `transform: translate(50px,20px) scale(1.2)` 后，`getBoundingClientRect().width` **读数完全没变**（923 → 923），因为它同时被 CSS 旋转与 Ken Burns 动画驱动。

→ **位置采集必须在"动效静止态"进行**，采集前先停掉动画。
→ 这是翻页变形最容易踩的坑：**你可能拿着一张错位的坐标图去做变形，而它不会报错，只会看起来"怪"。**

### C4 · 中文/CJK 的额外约束

- 无词边界 → 断行/拆字不能按空格，只能按字符
- 小字号下中文比拉丁文更容易糊 → 粒子化对中文的代价更高
- 需要确认字体加载完成再测量，否则坐标全部错位（`document.fonts.ready`）

## 4. 翻页变形：怎么做（重点章节）

用户反馈：*"这个变换效果我还没什么头绪。"* 以下是可执行的设计。

### 4.1 三条路线

> 命名说明：本节用 **A/B/C** 指代三条实现路线，避免与 §2 的需求编号 R1/R2/R3 混淆。

| | 做法 | 效果 | 代价 |
|---|---|---|---|
| **路线 A · DOM 行级** | 文本块整体做 transform 飞散/飞入，全程真文字 | 版块/整行飞散重组 | 低，零依赖 |
| **路线 B · Canvas/WebGL 粒子** | 文字渲染成点阵，逐字碎成粒子 | 最惊艳 | 文字**不可选中/不可搜索**，中文小字会糊，无障碍归零 |
| **路线 C · 混合快照** ← 推荐 | 见 4.2 | 两个都要 | 中等 |

### 4.2 路线 C 的核心思路：**读的时候是真文字，动的时候才变成像素**

1. **阅读态** → 纯真 DOM 文字（可选中、可搜索、可复制、无障碍满分）
2. **翻页瞬间** → 把当前版面**由引擎自己重绘一遍到 canvas**
   - 因为版面是我们排的，我们知道每个字块的**位置、字体、字号、内容**
   - 直接 `fillText` 精确重画，**不需要 html2canvas 那类截图方案** → 更准、更快、更可控
3. 在 canvas 上做粒子飞散 → 重组到下一页的字符位置
4. **动画结束** → 切回真 DOM 版面

**为什么这是护城河**：只有**自己负责排版**的引擎才能这么干。靠截 DOM 的外部工具做不到这个精度。这正是"渲染引擎"定位带来的独有能力——**如果只做聚合站，这招根本用不了**。

### 4.3 待解决的设计问题（开放）

- [ ] **字符数不等的映射**：A 页 800 字 → B 页 1200 字，粒子如何分配？（候选：先全碎→飘散→被 B 的位置吸附，不做一一对应）
- [ ] **粒子上限**：中文一页可能 800~2000 字，每字取 4~8 采样点 = 8k~16k 粒子（WebGL 轻松，Canvas2D 需实测 60fps）
- [ ] **时长**：暂定 0.8~1.2s。**超过 1.5s 会从惊艳变烦人**
- [ ] **可关 + 快慢两档**：连续翻页时自动简化；`prefers-reduced-motion` 必须尊重
- [ ] **图窗如何参与**：图片是碎成粒子，还是像纸片一样翻转？

### 4.4 副产品：翻页让项目有了"非视觉"的价值

既然要翻页，版面就从"一张静态图"变成**用报纸隐喻组织信息的界面**：头版 / 社会 / 科技 / 副刊 = 页面 = 栏目切换。

→ 这是防"看一次就腻"的关键结构。

## 5. 信息采集与 AI 主编（2026-09-21 范围扩展）

### 5.0 范围变更说明

立项时定的是"纯渲染引擎、聚合交给外部"。当日用户把范围扩展为**信息聚合平台**：项目自己从多个来源收集信息，并且**让 AI 来处理有限的版面容量**——选什么、怎么排、用哪张图。

**与 §0 定位的关系是分层，不是推翻**：

| 层 | 职责 | 备注 |
|---|---|---|
| 采集层 | 从 N 个来源抓取、去重、归一化 | 本项目 |
| **编辑层** | **在有限版面下做取舍与排布** | **AI，本项目核心创新** |
| 渲染层 | 把决策落地成版面 | 本项目，确定性引擎 |

> 聚合本身**不是**新东西（`goosepaper` / `unim.press` / `RSSPub` 都做了）。
> **新东西是：聚合之后由 AI 当主编做取舍。**

### 5.1 为什么"AI 当主编"是这个项目的正解

**理由一：这才是报纸的本质问题。**
一张报纸的版面容量就那么大（一版约 8~15 条），而来源每天给几百条。**取舍就是编辑工作的全部。** 这不是硬套 AI，是这件事本来就需要判断。

**理由二：它直接解决头号风险"看一次就腻"。**
纯视觉的活报纸只是一个壳——看第二遍就腻。但"今天 AI 主编判断头条是这个、那条只配一块豆腐块、另一条干脆不上"，让每一期都有**判断**可看、有**差异**可讨论。**这是把项目从"好看"变成"有用"的关键。**

### 5.2 分层架构（AI 只碰"决策"，不碰"渲染"）

```
数据源(N 个)
   ↓  采集：抓取 / 去重 / 归一化
条目池（几百条）
   ↓  粗筛：规则打分（可复用信息台已有的六维重要性评分）
候选池（几十条）
   ↓  ★ AI 主编：输出结构化的「编辑决策」
版面决策（JSON）
   ↓  排版引擎：确定性执行
活报纸版面
```

**硬架构约束：AI 绝不直接产出 HTML / CSS / 坐标。**

理由：AI 出错时，最坏情况应该只是**"选题选得不好"**，而**绝不能是"版面崩了"**。渲染质量必须由确定性引擎保证，与模型的稳定性解耦。

### 5.3 AI 主编的输入 / 输出契约

**输入**（每条都已经过归一化与粗筛）：

```
{ id, title, summary, source, source_tier, published_at,
  score_breakdown: { 信源等级, 影响面, 独家性, 证据强度, 可逆性, 后续钩子 },
  assets: { images[], has_video, aspect_ratios[] } }
+ 版面容量约束（几个板块、各放几条、头条位尺寸）
```

**输出**（结构化编辑决策，不是自由文本）：

```jsonc
{
  "issue": { "date": "...", "lead_id": "..." },
  "sections": [
    { "name": "头版",
      "blocks": [
        { "item_id": "...",
          "weight": "lead | feature | brief",
          "image": { "use": true, "asset_id": "...",
                     "crop_focus": [0.5, 0.35],
                     "motion": "kenburns | video | none" },
          "headline": { "style": "normal | large", "keep_original": true } }
      ] }
  ],
  "dropped": [ { "item_id": "...", "reason": "..." } ],
  "editor_note": "本期判断的一句话说明"
}
```

必须满足：

| 要求 | 说明 |
|---|---|
| **可解释** | 每条被丢掉的都要写 `reason`，便于人工复核与调参 |
| **可复现** | 同输入同输出（低温度 + 固定模型版本） |
| **可离线** | 决策结果缓存；同日重开不必重跑 |
| **失败可回退** | LLM 不可用时退化为"按规则分数排"，**版面照常出** |

### 5.4 红线（内容合规，不可协商）

> **AI 只能"选择和排布"，不能"改写和编造"。**

- ❌ 不许改写标题/摘要成原文没有的事实
- ❌ 不许替原文补充背景、数字、引语
- ❌ 不许生成"看起来像原文、但其实不存在"的句子
- ✅ 允许：截断、选择、排序、分组、决定字号、指定栏目标签

**理由**：本项目服务于真实内容生产（用户阵地：公众号 / 头条号 / 小黑盒），**编造事实会直接变成发布事故**。

**落地方式**：AI 的输出里**不含任何新句子**——`keep_original` 默认且只能是 `true`，版面文字一律从原文切片而来。这条用代码强制，不靠提醒。

### 5.5 成本控制

条目池有几百条，全量塞给 LLM 既贵又没必要。两级漏斗：

1. **规则粗筛**（≈0 成本）：复用信息台已有的六维重要性评分 → 几百条降到几十条
2. **AI 精排**（一次调用）：只对候选池做判断，一次输出整版决策

预期：每期一次 LLM 调用，结果缓存。**具体 token 量在实现时实测，此处不估。**

### 5.6 图片处理

三件事都由 AI 主编决策，但**执行在引擎**：

| 环节 | 决策（AI） | 执行（引擎） |
|---|---|---|
| **选哪张** | 从条目候选图里挑 | 图与稿结构绑定，不许错配 |
| **怎么裁** | 给出 `crop_focus` 焦点坐标 | 按栏位宽高比裁切；⚠️ 源图比例各异，不懂裁切就会切掉主体或拉伸变形 |
| **动不动** | `motion: kenburns / video / none` | video 走 motion provider，离线预生成 + 缓存 |

> **"哪张图值得花算力生成视频"本身就是一个编辑判断**——这既是 AI 该做的，也是最有效的省算力闸门。

## 6. 风险（按严重度）

| # | 风险 | 说明 | 对策 |
|---|---|---|---|
| 1 | **"看一次惊艳，用第二次就腻"** | 头号风险。若只是好看的壳，半年后沦为 demo 仓库 | **AI 主编的编辑判断是对策的核心**（每期都有判断可看）。辅助：①给内容阵地产封面/配图/短视频（最确定）②大屏信息台 ③给他人站点当嵌入组件 |
| 2 | **AI 编造事实** | 内容合规红线，会直接变成发布事故 | AI 输出**不含任何新句子**，只允许选择/截断/排布；`keep_original` 由代码强制为 `true`（§5.4） |
| 3 | **AI 决策不可复现/不可解释** | 无法调参、无法追责，用户不敢用 | 强制 `dropped[].reason`；低温度 + 固定模型版本；决策结果缓存落盘（§5.3） |
| 4 | **IP 红线** | **禁止**用 Daily Prophet / 魔法日报 / 哈利波特素材命名或做视觉。华纳法务出名 | 原创命名（已定 `movable-type`）。正因为这个领域被"玩具化"，原创做真东西才有机会 |
| 5 | **零配置体验** | 面向全球开发者，clone 下来必须一条命令看到效果，否则没人 star | 内置示例数据 + 一键 demo + GitHub Pages 活演示 |
| 6 | **动效过度** | 天天用会烦 | 全部动效可关、可调、有时长上限；尊重系统 reduced-motion |
| 7 | **C 档画质/速度不确定** | 本地 i2v 的质量与耗时**尚未验证** | **尽快跑样片** |
| 8 | **AI 决策成本失控** | 几百条全量喂 LLM 会很贵 | 两级漏斗：规则粗筛 → AI 精排（§5.5）；结果缓存 |
| 9 | **中文排版细节** | 断行、标点挤压、避头尾 | 列为独立需求项，不混在动效里做 |

## 7. 命名与定位

- **仓库名**：`movable-type`（GitHub 同名仓库实测 **0 个**）
- **为什么好**：
  - **活字印刷** = 排版之祖，正好是"信息 → 版面"的本源
  - 字面 = "**可移动的字**"，与"翻页时文字散开重组"是**同一个意思**
  - 带连字符，与老牌 CMS `movabletype`（432★）天然区分
- 备选（均查过占用）：`living-print`（0 个同名）、`inkwell`（⚠️已有 3018★ 项目，不建议）

## 8. v1 范围

**v1 要证明的一句话**：*一条命令，把任何 RSS 变成一份会动的报纸。*

**做**：
- **采集层：多源抓取 + 去重 + 归一化**（可先复用信息台现成实现）
- **AI 主编（最小版）**：粗筛 → 一次 LLM 调用 → 结构化版面决策
- Paper Model schema + 渲染器（零依赖）
- 单页版面 + 报纸主题（纸纹/铅字/双线/首字下沉）
- 动效 3 个：Ken Burns / 墨迹擦入 / 纸面波浪
- **翻页行级飞散（路线 A）** ← v1 招牌
- 本地 ComfyUI i2v 可选接入（provider 之一）
- 内置示例数据 + GitHub Pages 活演示

**不做**：
- 云 API 视频（等 key）
- 粒子级飞散（路线 C → v1.1，作为渐进增强）
- 账号系统 / 多用户 / 服务端
- AI 改写/生成正文（**永久不做**，见 §5.4 红线）

**明确推迟**（用户已表态，靠时间打磨）：
- 高质量文生视频 / 图生视频——先接占位视频与 GIF，等算力与模型成熟

## 9. 目录结构（提案）

```
movable-type/
├─ README.md              # 英文主 + 中文版；第一屏是 GitHub Pages 活演示
├─ docs/
│  ├─ REQUIREMENTS.md     # 本文档
│  ├─ PAPER-MODEL.md      # 版面模型 schema（待写）
│  ├─ EDITOR.md           # AI 主编的输入/输出契约与提示词策略（待写）
│  └─ MOTION.md           # 动效与翻页变形设计（待写）
├─ packages/
│  ├─ collector/          # 采集层：多源抓取 / 去重 / 归一化
│  ├─ editor/             # AI 主编：粗筛 → 版面决策（唯一碰 LLM 的层）
│  ├─ core/               # Paper Model + 排版引擎（零依赖，不碰网络）
│  ├─ theme-print/        # 报纸主题
│  └─ motion/             # kens-burns / ink-reveal / paper-wave / page-turn
├─ adapters/              # rss / json / markdown
├─ motion-providers/
│  ├─ none.js             # 默认：Ken Burns
│  └─ comfyui.js          # 本地 DynamiCrafter
├─ examples/              # 内置示例数据 + 静态 demo
└─ tools/render-mp4.mjs   # 版面 → 短视频
```

**分层依赖方向（单向，不许回环）**：

```
collector → editor → core → theme/motion
```

`core` 必须能在**完全离线、无 LLM**的情况下独立工作（喂它一份 Paper Model JSON 就能出报纸）——这条保证了引擎的可测试性，也保证 AI 挂了版面还在。
