# 事件追踪 · 产品与技术实施规格

> 日期：2026-10-17。对应 REQUIREMENTS.md §13 / R15–R19；含同日新增的主动历史检索与实验预测设计。
> 状态：下一版本设计草案，可用于拆开发任务；本文的数值是首轮试验默认值，不代表已验证结论或已确认排期。不包含实现代码。

## 1. 交付目标与边界

交付一份有记忆的日报：大部分普通内容继续提供随机发现机会；用户主动追踪的事件跨期积累，在出现新增事实时更新；打开故事线可以看到关注前后的发展，以及有证据支持的相关支线；关闭追踪后保存已有记录。

首轮以本机单用户为使用场景，不做账号、云同步、外部通知、AI 生成故事正文或完整新闻档案库。继续使用现有报纸渲染与原文切片规则。主动外部历史检索与独立实验预测分阶段接入，详见 §12–§15；预测不属于首轮事实追踪闭环。

实现必须保留现有链路的独立性：没有追踪数据库、没有 LLM 或没有网络时，缓存新闻仍可生成报纸。新增模块输出结构化数据，不能让模型生成页面代码或坐标。

## 2. 先定清楚四种对象

| 对象 | 定义 | 示例（虚构，仅解释结构） |
|---|---|---|
| 报道 | 某个来源发布的一篇文章，具有独立链接与发布时间 | 甲媒体报道某公司收购乙公司 |
| 事件故事线 | 围绕一个具体主体、行动与对象持续发展的过程，有稳定标识 | 某公司收购乙公司的全过程 |
| 进展节点 | 事件中的一次实质变化，多篇报道可共同支持同一节点 | 宣布收购、提交审查、获得批准、终止交易 |
| 支线关系 | 另一事件与本故事线某个节点之间有来源依据的联系 | 一项规则变化被报道明确关联到这次审查 |

“某公司”“人工智能”是实体或宽泛议题，不能直接当作单一事件。首轮仅支持具体事件；过宽的追踪请求提示用户选定某篇报道对应的事件，不静默创建无限扩张的主题订阅。

同一报道可以提到多个事件；同一进展可以有多个报道来源；同一支线事件可被多条故事线引用。禁止仅因主体相同就合并事件。

## 3. 模块、存储与部署方式

处理顺序：采集 → 报道归一化 → 事件候选匹配 → 事件归属 → 新进展判定 → 证据校验 → 持久化 → 日报选稿 → 生成展示快照。

- **采集模块**：沿用 newsdesk 的来源与失败缓存能力，负责获得材料，不决定主支线。
- **事件处理模块**：负责归并、进展、关系及证据；在全量合格材料中处理追踪匹配，不能只处理现有粗筛后的 48 条，否则会漏掉低热度的重要后续。
- **追踪管理模块**：负责用户状态、关注时间、已读位置与归档快照。
- **选稿模块**：负责普通探索、公共重要信息与追踪更新的版面配额。
- **渲染模块**：接收已验证快照，沿用确定性排版。故事线先用列表与展开面板，不以复杂图谱作为前提。

本机持久数据建议使用一个 SQLite 数据库，替代只覆盖 latest.json 的长期保存方式；原始采集快照、模型决策日志与展示快照分开保存。数据库是状态来源，HTML 是可重建产物。

追踪版本采用本地页面加本地服务：用户操作由服务写入数据库，随后页面更新。服务只监听本机，对修改操作校验请求来源及本地会话凭据。纯静态演示继续可用，但没有本地服务时明确显示只读模式，不展示会伪装保存成功的按钮。不要同时用浏览器 localStorage 和数据库维护两份独立追踪状态。

## 4. 最小数据契约

以下为概念字段，开发时可调整表名，但不能丢失身份、证据与时间信息。

| 记录 | 必须保存的信息 |
|---|---|
| 报道 Article | 稳定 article_id、原始及规范链接、来源、原文标题、可用原文片段、内容版本、发布时间、收录时间、抓取状态、时间精度 |
| 来源 Source | 来源标识、来源类别、可追溯的原始发布方；“聚合平台”和“原始来源”分开保存 |
| 事件 Event | 永久 event_id、原文标题选段作为显示名、主体/行动/对象候选、首次发现时间、身份版本、合并后的指向关系 |
| 进展 Node | 永久 node_id、所属事件、节点类型、原文标题/片段引用、发生时间及精度、可排序时间及其依据、首次收录时间、版本、状态 |
| 证据 Evidence | article_id、内容版本、片段位置或内容哈希、原文摘录、支持的节点或关系；即使原页面变化也能解释当时依据 |
| 关系 Relation | 两端事件/节点标识、关系类型、证据引用、待确认/已接受/已驳回状态、决策版本 |
| 用户追踪 Follow | 用户本地标识、event_id、active/archived、首次关注时间、各次启停区间、已读更新序号、归档时可见版本 |
| 展示批次 Issue | 期号、生成时间、入选标识及版本、随机种子、各分区配额、来源新鲜度、算法配置版本 |
| 处理记录 Run | 输入指纹、处理阶段、规则/提示词/模型版本、结果、耗时、重试次数与错误分类 |

证据不以模型自由文本代替。日期等提取值须能定位到来源，未知填空；发生时间、发布时间、收录时间都使用明确时区，原始时区与日期精度保留。长期议题采用永久 ID，不能用本次候选序号 i0/i1 或每天变化的标题作为身份。

## 5. 每日处理流程

### 第一步：采集与归一化

**输入**：来源配置、上次成功采集时间、缓存。

**处理**：沿用增量采集并保留一个可配置的重叠窗口，防止延迟报道漏入；规范链接时只移除已知跟踪参数，不删除可能区分文章的查询参数。优先用来源自身文章 ID，其次规范链接生成报道身份。链接相同而内容变化时保存内容版本，不另建无关报道。

**输出**：新报道、发生变化的报道、来源状态。HTML/脚本先清洗；来源文本视为资料，不作为模型指令执行。

**验收**：相同输入重跑不重复建报道；同链接更新不丢旧版本；失败源不会被当作“今日没有新闻”，缓存材料显示原始时间与过期状态。

### 第二步：质量检查与候选分流

**输入**：归一化报道与活跃追踪清单。

**处理**：先过滤空标题、无效链接、明显广告与采集错误。材料不足的报道可保留标题及链接，但不能据此推断复杂进展。分别进入普通新闻候选池、事件匹配候选池；追踪匹配不受通用新闻热度排名截断。

**输出**：合格报道、暂缓材料及理由。

**验收**：一篇评分低但与活跃事件直接相关的报道，仍能进入事件判定；未读到正文必须明确材料范围。

### 第三步：找到可能属于同一事件的材料

**输入**：新报道、已有事件及最近节点。

**处理**：先用主体、行动、对象、时间范围与原文关键词检索候选；标题相似度只作辅助。首轮每篇最多取 5 个候选事件供后续判断；没有可靠候选时允许新建事件。是否引入向量检索取决于召回测试，不作为首轮必要依赖。

**输出**：报道与候选事件的配对，附检索依据。

**验收**：同公司不同收购不合并；跨语言但描述同一交易的报道能成为候选；跨月事件不会因超过新闻时间窗而丢失身份。

### 第四步：判定事件归属

**输入**：候选配对、报道原文片段、事件已有证据与节点。

**处理**：规则优先确认明确的相同原始公告或事件标识；不明确的配对交给模型选择“同一事件 / 独立但可能相关 / 无关 / 材料不足”。模型只输出结构化分类、候选 ID 与证据片段引用。校验器检查 ID 存在、引用确为输入原文、归属不冲突。

**输出**：已接受归属、独立事件或待确认项。模型自报置信分仅记录，不独立决定是否发布。

**验收**：证据不足时保持独立或进入待确认，不强行合并；任一自动归属能回查证据与决策版本。

### 第五步：判断有没有新进展

**输入**：同一事件的新材料与已有节点证据。

**处理**：比较主体、动作、状态、结果、日期与关键原文片段，分类如下。

| 判定 | 系统行为 |
|---|---|
| 同事实转述 | 追加来源引用，不新增故事节点、不增加未读进展数 |
| 新增实质事实 | 创建新节点；正文仍使用原文片段 |
| 同节点的补充证据 | 更新节点版本；只有实质改变理解时才生成更新记录 |
| 说法相互冲突 | 保留双方证据并标记“来源说法不一致”，不得自行裁决哪方为真 |
| 更正或撤回 | 关联旧节点，标记其状态，建立更正记录；旧记录可追溯 |
| 无法确定 | 暂缓进入正式故事线，保留待确认材料 |

**输出**：节点变更集合及是否值得展示的更新记录。媒体数量变化不等于事实变化；报道措辞“官方宣布”不等于已独立核实。

**验收**：同一公告被十家媒体转述只产生一个进展；官方更正可以改变旧节点状态；没有新增材料时显示暂无新进展。

### 第六步：保存与建立主支线

**输入**：通过验证的节点、独立事件及关联候选。

**处理**：先持久化直接进展，主线按事件自己的变化组织。支线必须指向独立事件或其中节点，并引用明确支持关系的原文。关系类型首轮限制为“来源明确提及的关联”“程序上的前置事项”“来源明确描述的影响”，不要生成无来源的因果结论。

仅主体相同、同属行业或发布时间接近，不足以发布为支线。模型建议但证据不明确的关系留在待确认区；首轮由本地维护者人工接受或驳回。关系方向仅在来源支持时展示。

**输出**：正式主线、已接受支线、待确认关系。

**验收**：每条公开支线都能展开依据；删除错误关系不删除其独立事件；跨故事线引用同一支线时保持同一身份。

### 第七步：确定本期内容

**输入**：合格普通新闻、公共重要信息候选、活跃追踪更新、已读位置。

**处理**：首轮以每期 20 个展示名额试验：随机探索 12 个、公共重要信息 4 个、追踪更新 4 个。比例可配置，不能根据个人点击行为自动改变。

- 公共重要信息使用公开规则独立筛选，参考影响范围、紧迫性与可核验证据；不使用个人兴趣作为排除条件。来源不足的高风险消息不能仅凭高分当作已证实消息置顶。
- 随机探索先按新闻类别分层轮换，再在合格候选中抽样；不按来源文章数量直接抽，以免高产来源淹没其他来源。候选充足时，同一来源不超过探索区名额的四分之一。
- 抽样种子按期保存；同一期重建不反复洗牌。已展示事件在连续三期内原则上不重复进入探索区，除非有实质新进展；这是去重规则，不是兴趣画像。
- 追踪更新按更正/重要状态变化优先、再按未展示时间排序，每事件默认占一个名额；所有更新仍可在追踪列表查看，版面放不下不等于丢弃。
- 同一内容占多个分区时只展示一次，可附多个标签；先预留公共信息与追踪名额，再抽探索内容。
- 追踪名额不足，转给随机探索；公共信息不足，也转给随机探索。不得用转述或低质量材料硬凑；全部候选不足时显示实际数量。
- 公共重要消息超出配额时，用额外的“重要消息补充”区域展示经筛选的溢出项，不挤占 12 个探索名额；说明超出原因。已连续展示的消息没有新变化时转为持续提示，避免无限重复占位。

**输出**：稳定的期刊清单、配额使用记录、未展示更新索引。

**验收**：只关注科技事件也能看到其他类别；关闭全部追踪仍有完整日报；同一期可按保存的输入版本和种子复现选稿。

### 第八步：发布快照与失败回退

**输入**：已落盘的节点版本与期刊清单。

**处理**：一次批次成功后才切换可见快照；模型输出先校验再作为正式决策缓存。缓存键含输入材料版本、规则/提示词版本、模型标识及相关配置，保存实际输出，不能靠低温度保证复现。

**输出**：报纸页面、追踪列表、事件详情与批次状态。

**验收**：模型失败时继续出普通报纸，故事线保持最后成功状态并提示本轮未完成检查；抓取失败不能显示“确认无新进展”；单事件失败不阻塞其他事件；中途退出后重跑不重复追加节点。

## 6. 用户操作如何执行

### 开启追踪

1. 用户点“追踪这件事”，展示已有事件标题与范围，确认要追踪的具体事情；不根据阅读行为代点。
2. 服务检查是否已有活跃追踪：已有则打开详情，不重复创建；新关注先保存关注时间与当前事件关联。
3. 立即展示已知节点，历史回溯单独排队，不能为了等回溯完成而阻塞追踪成功。
4. 操作失败显示未保存并允许重试；只有落盘成功后才显示已追踪。

### 查看日报与详情

日报增加“追踪进展”区域：事件标题、本次新增数量、最近更新日期，以及进入脉络的入口。不要把已归档事件混入此区域。

详情默认先展示关注后的节点，标出关注时间分界，可展开关注前历史。节点展示原文标题/片段、时间依据、节点状态、来源与支线入口。支线默认折叠，展开时先看关联证据，再进入该事件详情，避免首屏成为复杂网络。

“已读”以用户点击“标记本次已读”为准，不把进入页面等同于理解所有内容。已读位置使用更新序号，而非只用事件发生时间，保证晚到的历史材料与更正不会被遗漏。历史补齐与新进展分别计数。

### 关闭与归档

用户点“结束追踪并归档”后，将状态改为 archived，记录关闭时间、最后可见版本与节点集合。移出每日追踪更新，不再为其启动专用补采任务。普通采集仍可能获得相关新闻，它可以按普通新闻规则出现，但不恢复追踪。

首轮提供简单“已归档”列表，可重读冻结快照；完整全文检索后置。其他活跃故事线可继续引用同一事件，不能因为一个用户归档就冻结全局事件。归档快照与全局持续演化的数据分开。

来源更正或撤回涉及归档内容时，可附加醒目的更正标记并保留归档原版本，不能继续无提示呈现已知失实内容；这不恢复日常追踪。首轮不做恢复追踪入口，后续设计需明确停追期间如何补齐。

## 7. 历史回溯如何做

1. 开启追踪后先查本地已有报道与事件记录，默认回溯关注前 30 天，最多展示 20 个已验证历史节点。时间窗和数量作为试验参数。
2. 最小闭环阶段先用本地材料；随后加入用户主动发起的外部历史检索，按 §12 执行。本地不足时显示“当前仅覆盖已采集材料”，允许维护者导入具有来源的历史报道，经过同一归并与验证流程。
3. 回溯材料按发生时间插回历史位置，但保留新收录标记；不能伪装成当时已知的信息。发生时间未知时按发布时间排列，并明示依据；两者皆未知则进入“时间待确认”区，不伪造精确日期。
4. 区分“历史补齐”和“今日新进展”，避免把一年前发生、今天收录的事推成今日新闻。
5. 外部检索的范围、预算与失败策略按 §12 执行；具体检索 provider 选型在开发时验证，无材料不能由模型凭记忆补齐。

## 8. 纠错、合并与拆分

首轮给本地维护者提供最小纠错入口：移出错误节点、改归属、接受/驳回支线、合并/拆分事件、标记来源更正。每次操作保留原因与前后版本，重新生成受影响快照。

- 合并事件时保留旧 ID 到新 ID 的映射，迁移追踪关系并去重；旧链接仍能找到新事件。
- 拆分事件时保持节点身份，分别指定新归属。原追踪进入“范围待确认”提示，不能静默扩成多条订阅；用户确认前暂停该追踪新增展示，其他日报照常生成。
- 归档快照保留当时版本，涉及身份变化显示映射提示；涉及事实错误附更正，不静默抹去原记录。

## 9. 运行预算与可观察性

首轮建议同时活跃追踪上限 10 条，每天随出报执行一次检查；超限在创建前说明，不悄悄忽略。历史任务与日常更新分开排队，日常更新优先。

模型只处理规则无法明确判定的候选，按事件批处理。每次运行设可配置的调用次数、总 token 与超时预算；实际费用在选定 provider 后测量，不在文档中假设固定价格。预算耗尽后剩余项进入待处理，页面显示未完成检查。

后台记录采集成功率、待处理数量、错误归并数量、证据校验失败数、重复节点数、更新延迟及调用成本。页面仅展示读者需要理解的新鲜度和缺口，具体堆栈与模型日志留给维护者。

本地数据默认不自动过期，归档不会删除证据；提供备份/导出与显式删除能力。删除共享事件前检查其他故事线引用，单独删除用户追踪记录不能破坏共享事实。跨设备与云备份后置。

## 10. 开发拆分与阶段门槛

| 顺序 | 开发交付 | 完成标准 |
|---|---|---|
| A：数据基础 | 永久 ID、数据库、证据版本、运行记录、旧采集数据导入 | 输入重跑无重复，旧链接可追溯，不影响现有出报 |
| B：最小追踪 | 本地服务、主动关注、列表、直接进展、跨期保存、归档快照 | 同一事件连续多次出报仍为同一故事线；关闭后停止更新 |
| C：进展质量 | 转述合并、冲突、更正、失败状态、人工纠错 | 不将转述计作进展，不隐瞒来源矛盾，模型失败不丢状态 |
| D：分发与阅读 | 三分区配额、稳定抽样、未读记录、详情时间线 | 未关注领域仍可见，晚到更新不漏读，缺额有明确回补规则 |
| E：历史与支线 | 本地回溯、关注分界、有证据的支线、关系复核 | 历史与新进展分开，所有公开关系可追溯依据 |
| F：主动历史检索 | 按周/月查询外部历史、证据验证、覆盖矩阵、材料导出 | 每个历史节点可溯源，未检索与无结果分开，详见 §12 |
| G：实验预测 | 独立情景区域、概率版本、到期判定与校准记录 | 事实与预测隔离，旧预测不可覆盖，详见 §13–§15 |
| 后续评估 | 完整档案库、恢复追踪、长期议题 | 根据前述使用结果另定范围，不阻塞首轮 |

B 完成即可内部试用；C、D 完成后再进行连续使用验证；E 分批加入。上线日期根据实际工作量另定。

## 11. 验证样例与试用标准

开发前建立人工标注的小型材料集，包含至少 10 个事件、合计 100 篇报道，覆盖同主体不同事件、中英同事件、同事实多源转述、真实新进展、跨月更新、日期缺失、历史晚到、更正撤回与无证据的相似话题。样例用原文及人工预期判断，不用模型自评代替验收。

功能验收必须覆盖：

1. 连续重跑同一输入，报道、节点、追踪及未读数不重复增长。
2. 两篇主体相同但行动对象不同的报道不被错误合并；不确定项可暂缓。
3. 十篇转述形成一个节点，多来源可展开；实质更正进入更新列表。
4. 关注前历史与关注后进展可区分，未知时间不会生成精确日期。
5. 没有来源支持的支线不公开展示；修改错误关系不损坏其事件。
6. 归档后不新增追踪更新，归档时内容仍可读；全局事件仍能服务其他追踪。
7. 无网络、模型故障、输出不合法、预算耗尽与本地服务关闭均有明确降级状态。
8. 用户只关注单一领域时，探索区仍包含其他可用类别，配额不会因点击自行收窄。

首轮质量目标：公开节点与支线证据引用有效率 100%；样例集事件归属精确率至少 95%，新进展识别精确率至少 90%。同时记录漏归属、漏进展与暂缓比例，不能用全部暂缓换取表面精确率；按预留的独立样例验收，未达标则收紧自动发布、增加人工复核。

连续试用两周，记录实际展示过的事件、来源、类别及用户反馈，重点回答：重复内容是否减少、读者能否准确说出本次变化、是否误把支线当因果、重要信息是否被遗漏。点击率只作为辅助观察，不作为优化目标。

## 12. 主动历史检索与故事范围扩展

### 12.1 发起任务：先确定追踪的是什么

事件详情增加“补齐过去脉络”。用户选择故事范围、回溯起止日期与周/月粒度；默认先查最近三个月，允许向更早延伸。范围、预算及时间窗口都是可调整试验参数。

例如从“某次 GTA6 预告片发布”扩展到“GTA6 发布与上市过程”，先展示范围变更。较长过程作为 Story 容器，引用多个独立 Event，不把之前的单事件身份覆盖掉。Follow 可指向事件或故事容器；迁移须记录原范围、确认时间与原事件引用。公司整体、全体玩家仍不是无边界的自动订阅对象。

界面先展示任务计划：搜索哪些月份、优先哪些来源、预计请求上限、哪些时期已有本地材料。用户发起回溯不等于允许无限后台检索。

### 12.2 分窗口执行检索

| 步骤 | 处理规则 | 输出与失败行为 |
|---|---|---|
| 1. 建立查询画像 | 使用已验证的主体、作品名、官方别名、行动与目标，保留原文引用；不从未确认传闻扩写关键词 | 可编辑画像与故事范围版本 |
| 2. 切分时间窗 | 按月从近到远查询；信息密集或用户展开时再按周细分，边界采用明确时区与不重复的起止规则 | 窗口任务列表及覆盖状态 |
| 3. 本地召回 | 查询数据库已有报道与证据，复用已验证节点，仍显示材料时间范围 | 本地命中与待外查缺口 |
| 4. 外部检索 | 检索 provider 接收关键词、别名、时间范围、来源限制及分页参数；优先原始公告、公开记录，再补可信媒体与原始访谈 | 搜索结果只作候选，不直接生成节点 |
| 5. 读取原文 | 取得正文或可用原文片段，核对文章自身日期与所述事件日期；搜索引擎日期过滤不能保证事件发生于该窗口 | 原文证据、时间精度、访问限制 |
| 6. 归并与分流 | 复用 §5 的事件判定、转述合并、进展与关系校验；区分主线、支线候选、无关、待确认 | 已验证节点与可审查的排除理由 |
| 7. 挑选里程碑 | 优先状态改变、正式决定、结果、更正等节点；普通转述不增加里程碑。首屏每月最多 5 个里程碑，其余可展开，不删除底层证据 | 月/周概览与完整节点列表 |
| 8. 发布与保存 | 按真实发生时间插入；未知则显示排序依据。历史补齐单独计数，任务部分完成也可展示已验证部分 | 可追溯快照、缺口和未完成任务 |

初始预算建议：单任务最多 12 个月窗、每窗最多 2 个查询变体、每查询读取前 5 个候选原文；额度耗尽后暂停并显示覆盖范围，继续向前由用户再次发起。周细分、重试与翻页均计入总预算；provider 不支持日期过滤时，在原文验证阶段完成过滤并说明召回限制。

检索适配器至少返回原始链接、标题、摘要、结果日期及日期依据、查询参数、provider 与抓取时间。缓存按查询、窗口、provider 与版本区分；失败任务可断点恢复。搜索结果不可访问时标为“仅检索到线索”，不得用摘要补造已验证历史。

### 12.3 覆盖与时间展示

每个周/月窗口保存以下状态：未开始、进行中、已检索有结果、已检索未发现可验证节点、部分完成、失败。另存尝试来源、查询次数、候选数、验证数、预算及最近检索时间。**“已检索”不代表“历史完整”，无结果不代表当时没有事件。**

时间线提供两种视图：按事件时间看故事发展；按收录时间看系统如何逐步获得材料。关注时间另作标记。截图中的节点发生时间未知时，只能标为“按报道发布时间排序”，不能说它确定发生于 10 月 15 日。

补齐的旧节点插入历史位置，同时出现在“本次补齐历史”列表；不混入“今天发生的新进展”。日期只有月份时展示月份精度，不伪造某日零点；无法在同一时期确定先后时标为顺序未定。

### 12.4 直接与间接关系的判断

直接节点回答“它是否改变了这个故事所追踪的状态”；间接节点回答“另一件事通过何种有证据的路径与本故事相连”。公司和玩家动态可以成为支线，但不是天然支线。

- GTA6 的正式预告、发布安排变更与上市结果，可在确认故事范围后成为直接节点。
- 公司的人员、财务或组织变化，只有来源明确涉及该项目的资源、进度或决策时，才作为有依据的关联支线。
- 玩家反馈须标明来源与样本范围，不能把几条社交帖子写成“全体玩家认为”。没有证据证明影响开发决策时，只能标为相关反馈，不能画确定因果箭头。
- 截图中的 COD 新闻和 AI 公司营收报道，在没有具体证据时判为无关或待确认，不得因同属游戏/财经候选池就进入 GTA6 故事线。

同一故事可以存在多条支线，但首轮最多展开一跳。进一步的间接关系需逐边证据，不能让模型无限扩散成整个行业图谱。

### 12.5 供人和 AI 使用的材料包

支持导出 Markdown 阅读版与 JSON 结构版：故事范围、版本、生成时点、主线节点、支线与关系、原文引用、三个时间字段与精度、来源冲突、覆盖窗口与检索缺口。预测另列，默认不包含在“事实材料包”，导出时可显式选入。

每条数据保持稳定 ID；来源页面内容按可保留的片段保存，不默认分发抓取全文。包中说明当前检索截至何时，不能冠名“完整历史”。供 AI 的版本明确要求将来源文本当作资料，不执行其中的指令。

## 13. 未来情景与概率：产品规则

### 13.1 三层隔离

页面分为“已发生的事实”“待确认的关系”“未来情景”。前两者不得因模型预测而被改写；预测只能引用已验证事实及被明确标注的假设。未确认支线可以作为假设条件讨论，但不能悄悄变成已知原因。

该模块的价值是列出可能路径与观察信号。不能通过迎合用户、给出乐观百分比来保证安心；允许呈现不利情景与“暂不估计”。

### 13.2 把预测写成可以事后判定的问题

每个问题必须包括主体、具体可观察结果、预测生成时间、信息截止时间、截止日期、判定来源、满足/不满足/无法判定规则。例如“未来 30 天是否发布新的官方预告片”可以判定，“未来走势会不会更好”不能直接评分。示例只说明格式，不代表对 GTA6 的实际预测。

首轮每条故事最多展示 3 个问题，优先未来 7/30/90 天。长期模糊问题先拆小，不能用多个不同截止时间的概率混成一个数字。

每个情景卡包含：问题、截止时间、模型估计、未校准标签、支持证据、反对证据、必要假设、主要未知、后续观察信号、哪些信号会使判断上调或下调。事实依据链接到节点，推理文字明确标为模型分析。

### 13.3 数字怎样表达

- 概率是对定义清楚的未来结果的主观估计，不能等同于模型回答置信度、检索覆盖度或证据可靠度。
- 有估计依据时保存一个点估计用于事后评分，界面最多保留到 5 个百分点，不显示 73.62% 等伪精度；可另展示低/中/高及证据质量。粗略区间若展示，必须说明是敏感性范围，不冒充统计置信区间。
- 缺少有效依据、历史覆盖过窄或冲突无法厘清时输出“暂不提供概率”，仍可给出条件情景与观察信号。不能强制所有故事产生百分比。
- 同一截止时点下，互斥且穷尽的情景概率合计为 100%，必要时包括“其他”；相互可同时发生的预测各自估计，不要求相加为 100%。条件概率必须把条件写在问题上，不能与无条件概率混排。
- 没有同类历史样本时明确写“模型主观估计，未完成历史校准”；有样本时记录样本定义、数量、时间范围和选择方式，不能为了支持结论挑选案例。

## 14. 预测的技术处理与生命周期

| 环节 | 输入与处理 | 输出与校验 |
|---|---|---|
| 1. 冻结材料 | 选择信息截止时点，仅取当时已获得的事实与关系版本；列出检索缺口 | evidence_snapshot_id；之后补采的旧材料不能回填到旧预测输入 |
| 2. 定义问题 | 从当前故事状态提出可观察的近期结果，固定截止日及判定规则 | question_id、问题版本；不可判定的问题拒绝进入概率阶段 |
| 3. 构建基准 | 如有可比历史，计算并展示相同定义下的参考发生率；没有则记录缺失 | 基准材料及限制，不能编造基础概率 |
| 4. 分析情景 | 模型分别整理支持、反对和替代解释，区分事实与假设，给出暂定概率及变化信号 | 结构化情景；分析里的事实陈述逐项引用证据 |
| 5. 反向检查 | 检查误归属、漏掉反证、来源不独立、条件重复计算和不合理确定性；允许模型自检但不能视为独立核实 | 检查结果；关键事实无法验证则不发布数值 |
| 6. 发布版本 | 校验概率范围、互斥组和、时区、证据 ID、截止日期与问题状态；首轮由维护者复核 | 独立预测快照，不进入事实表，不当作下一次的事实来源 |
| 7. 更新 | 新增实质证据、更正或定义好的观察信号触发重估；用户可手动请求，普通转述不触发 | 新版本、旧值、新值、变化依据；保留全部旧版 |
| 8. 到期复盘 | 按原判定规则核对来源，记录发生/未发生/尚不能判定/问题失效；必要时由维护者裁决 | 结果与证据；不得为提高命中率改题或删掉失败预测 |

新增数据对象：BackfillJob 与 Window 保存检索范围、进度、预算和来源覆盖；Story 与 Membership 保存过程范围及事件引用；ForecastQuestion 保存可判定定义与截止日；ForecastVersion 保存概率、材料快照、模型/提示词版本、推理与假设；ForecastResolution 保存结果、依据与裁决记录。所有对象使用永久 ID 并保留版本。

概率模型失败时不发布新版本；旧版保留生成时点并标明过期状态。截止后冻结正常预测更新，只允许补记判定结果或更正记录。归档追踪后停止自动重估，已有预测与到期状态仍可查询，不静默继续消耗推理预算。

以信息截止时点为界保存材料十分重要：事件发生日期早于截止日，但系统后来才发现的报道，不能用于宣称旧预测“当时就知道”。历史回测也只使用当时可获得、且能够验证发布时间的资料；无法消除未来信息泄漏的回测明确标为探索性。

概率评估首先采用二元问题的 Brier 分数，即预测概率与实际结果（0 或 1）之差的平方，越低越好；固定使用每个问题预先约定的评分版本（首轮用首次发布版），更新版另作分预测提前量评估。对相互独立的问题适用二元评分，互斥多情景另设分组评分，不混算。

同时按概率区间展示实际发生率及样本数，观察声称约 70% 的问题是否长期接近相应频率。样本少时只报告记录，不声称已校准。比较固定基准与可用的同类历史基准，相关事件按事件组报告，不能把同一故事的许多相近预测当作大量独立样本。问题失效或无法判定单独统计并公布理由，不当作命中。

## 15. 新增开发顺序与验收

1. **先修关联质量**：把截图中的无关混入作为回归样例；不确定关联进入待确认，不先进入主线再让预测过滤。
2. **再做主动回溯**：确认故事范围、月份任务、原文读取、验证归并、覆盖矩阵、历史插入与导出。完成后即可独立交付，不依赖预测。
3. **再做条件情景**：先验证能否写出可判定问题、支持与反对证据和观察信号；此阶段允许没有概率。
4. **最后试验数字预测**：维护者复核少量问题，保存版本与结果；积累到期记录后再讨论数值质量，不将未校准概率作为头版新闻。

新增验收必须覆盖：

- 三个月检索可断点恢复，重复执行不重复建节点；无结果、未检索、失败的窗口表现不同。
- 搜索结果显示日期但正文实际描述更早事件时，不把搜索日期当作发生日期；月精度不渲染为精确日。
- 扩大故事范围须确认，原单事件 ID 不变；支线公司/玩家材料均有具体关联依据。
- 历史补齐只增加历史计数，不误报今日进展；导出包含证据、缺口与版本。
- 无效时间范围、检索预算耗尽、原文不可访问都能给出部分结果与状态，不伪造历史。
- 事实页面不出现预测句，事实导出默认不含预测；支持证据与反对证据均可追溯。
- 互斥情景概率校验、可同时发生的问题不强制归一；证据不足时允许无数字。
- 概率更新保留旧值与原材料；新发现旧新闻不能污染旧预测；截止后不偷偷改题。
- 不利结果、失败预测与无法判定都保留；小样本不展示“已验证准确率”。
